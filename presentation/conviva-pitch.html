01 · The Problem

The job-application paradox.

Generic resumes don't get interviews. Tailored ones do. But scale breaks the manual model.

~75%
of resumes never reach a recruiter — filtered out by ATS keyword gates.
45 min
average time spent manually tailoring a single resume to one job posting.
10×
more applications a candidate sends today vs. five years ago to land one role.
The math doesn't work. 45 minutes × 30 applications = 22 hours of editing per active job search week. Most people stop tailoring after the first five. That's where the funnel breaks.
02 · User & Insight

Built for the active applicant.

Not the curious browser. Not the "let me build a resume from scratch" persona. The person sending 10+ applications a month with high stakes per send.

● Who they are

  • Sends 10–50 applications/month
  • Already has a resume — wants it adapted, not rebuilt
  • Time-poor: applying during lunch, commute, evenings
  • High emotional load: each application is a chance
  • Recently laid off, bootcamp grad, switching industries

● What we learned

  • Will pay per success — subscriptions feel wrong
  • Trusts free preview before pay — login wall lives at download, not optimization
  • Wants history — applying to similar roles often
  • Refuses to lose original formatting — multiple template options matter
  • OCR fallback isn't optional — scanned PDFs are common

04 · Core Flow

Three steps, three product surfaces.

Each step has its own design rationale, error model, and instrumentation.

1

Extract

A resume isn't a string — it's a layered document. The extractor picks the right tool for the source.

  • unpdf for digital PDFs at the edge
  • mammoth for DOCX, lazy-loaded
  • Google Vision OCR for scans and images
  • MIME sniffing by magic bytes, not browser MIME
2

Optimize

The AI doesn't keyword-stuff. It rewrites bullets to match what the JD actually rewards.

  • Structured output: parsed into typed sections
  • Provider fallback chain prevents single-API outages
  • ATS score + keyword match returned with the rewrite
  • Latency budget: target p95 < 5s
3

Review & Download

Free to preview, gated at download. The pricing wall lands when value is already proven.

  • Side-by-side diff before login
  • Login only at the download click — no sooner
  • Template chosen post-payment, not before
  • Auto-saved entry in Resume History

07 · Analytics — Strategy

One metric forces every decision.

Pick a North Star that captures activation, monetization, and repeat use in a single number — then defend it.

North Star Metric

Successful Customized Downloads per Weekly Active User

S-CDPWAU = Σ download_succeeded(week) / Σ WAU(week)

Why this metric

S-CDPWAU
Activation rate Visit → first download. The "first value" gate.
Repeat rate Downloads / user / week, conditional on WAU.
Funnel conversion Upload → completed download. End-to-end fidelity.

✓ Captures activation, monetization, and repeat use in one number. ✗ Doesn't reward vanity volume (visits or signups without payment).

Counter-metrics

  • Error rate — fewer crashes, higher NSM is meaningless if reliability degrades
  • Refund rate — a forced download is worse than no download
  • Time-to-value (TTV) — speed is the promise; protect it
  • CAC — bought users don't compound

09 · Analytics — Product QoE

Product QoE — borrowed from streaming analytics.

Conviva measures viewer experience in real time. The same playbook applies here: latency, success, errors, engagement — measured per session, surfaced as SLOs.

Streaming QoE

  • Video Start Time — time from request to first frame
  • Rebuffering Ratio — wait time / total time
  • Bitrate — quality of stream delivered
  • Failure Rate — abandoned starts, fatal errors
  • Concurrent Users — real-time load
  • Engagement — watch time, completion %
↔

PixelPear Product QoE

  • Time-to-First-Extract (TTFE) — upload → preview shown
  • Time-to-Optimized (TTO) — click → comparison rendered
  • AI Latency p50/p95/p99 — per provider, per region
  • Extraction Success Rate — by file type & method
  • Active Optimization Sessions — real-time load gauge
  • Engagement — time on comparison · scroll depth

10 · Analytics — Operating It

Future Steps: Experiment, respect, ship — then compound.

Analytics is only useful if it changes decisions. The stack and the principles below are what turn a funnel into a flywheel.

⚗ Experimentation

  • Cloudflare KV-backed feature flags — server-side bucket assignment, no flicker
  • Stat-sig calculator gated to ≥ 95% confidence before ship
  • One experiment per funnel stage at a time, sequenced by impact
  • First test: pricing card layout v1 vs v2 → primary metric: payment_completed rate

⛨ Privacy (resumes are PII)

  • Hashed user IDs in analytics — never email or raw name
  • Never send raw resume content to analytics — chars yes, text no
  • GDPR / CCPA: delete-history and export-history endpoints
  • PII vault separate from analytics warehouse; least-privilege access

⚙ Stack

  • Client SDK · PostHog (self-host option for cost control)
  • Server events · Workers Analytics Engine + custom fanout
  • Warehouse · BigQuery (or D1 → R2 → DuckDB for MVP)
  • Viz · Looker Studio / Metabase · Alerting · PagerDuty on SLO breach

↗ Roadmap (next 90 days)

  • ✓ Resume History — auto-named, local-first shipped
  • Cross-device history via D1 sync (login-gated)
  • SLO: TTO p95 < 5s · TTFE p95 < 2s
  • Cohort retention dashboards + weekly experiment readouts
